# Changelog

All notable changes to the `hmftools` module will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.1] - 2021-12-29

- Updates to the GRIDSS-PURPLE-LINX pipeline, incorporating new and better ways of handling unmatched tumours. 
- Added two small, additive prerequisite rules for the new `neo` module (HMF Tools' NEO neoantigen prediction), deliberately kept separate from `_hmftools_linx`/`_hmftools_purple_matched` themselves rather than adding to those rules' own `output:` lists -- under `--rerun-triggers mtime`, adding a new required output to an *existing* rule would make every already-completed sample look incomplete and force a rerun (LINX, and worse, PURPLE-and-everything-downstream-of-it) just because a newly-declared file didn't exist yet for old runs:
    - `_hmftools_linx_neo_epitopes`: re-invokes LINX with the exact same real inputs `_hmftools_linx` already uses, plus `-write_neo_epitopes` (confirmed to already exist in the pinned `hmftools-linx=1.15` by downloading the closest real release jar, `linx-v1.16`, and finding the literal string compiled into `FusionDisruptionAnalyser.class` -- no LINX version bump needed), into its own output directory. Costs one redundant LINX invocation per pair that wants neo-epitope output, but leaves `_hmftools_linx`'s own already-completed output completely untouched for every other sample/user.
    - `_hmftools_output_purple_somatic_vcf`: PURPLE already writes a real `<tumour_id>.purple.somatic.vcf.gz` as a standard side-effect of being given `-somatic_vcf` (which `_hmftools_purple_matched` already does) -- it was simply never declared as a tracked output. This rule depends only on one of `_hmftools_purple_matched`'s own *already-tracked* outputs (`purity.tsv`) as a dependency anchor for correct ordering/staleness, then symlinks the adjacent, already-real file directly -- `_hmftools_purple_matched`'s own `output:` is completely unchanged.
    - Both verified via a real local dry-run against demo data, including a real simulation of "PURPLE and LINX already completed" (their own declared outputs pre-touched with correctly-ordered timestamps) confirming neither rule appears in the resulting job list -- only the two new rules and their own downstream consumers do.
- Fixed a real crash found on a real cluster run of `neo`: `_hmftools_output_purple_somatic_vcf` symlinked only the `.vcf.gz` itself, dropping PURPLE's own companion `.tbi` tabix index (which PURPLE, like every other VCF-writing tool in this family, writes automatically alongside it). `modules/neo/1.0`'s `_neo_pave_annotate` reads this VCF via htsjdk, which requires an index physically alongside any VCF it opens, and crashed (`TribbleException: "An index is required, but none found."`) the moment it was pointed at the symlinked-but-unindexed copy -- PURPLE's own, un-relocated output directory was never affected, only the relocated symlink. Fixed by adding a second `somatic_vcf_tbi` output that symlinks the adjacent, already-real `.tbi` the exact same way the VCF itself is symlinked; added to `_hmftools_all`'s own target list alongside the VCF.
- Found a real, version-specific filename mismatch on the same real cluster run, immediately after the fix above: `_hmftools_linx_neo_epitopes` completed with no errors (confirmed via the real job log: known fusion data loaded, SV analysis completed) but never produced its declared `<sample>.linx.neoepitope.tsv` output. Root cause: this module actually installs LINX 1.17 (confirmed via that same real log's own `LINX version: 1.17` line), which really writes `<sample>.linx.neo_epitope.tsv` (underscore before "epitope") -- a real, different filename convention than the `<sample>.linx.neoepitope.tsv` (no underscore) constant this rule was originally verified against on LINX's newer `master` branch source. Initially fixed with a same-directory `ln -sf` compat symlink under the no-underscore name -- **superseded below**, see next bullet.
- **Superseded the fix above**: the compat symlink let `modules/neo/1.0` find and read the file, but reading it then crashed with a `NullPointerException` -- LINX 1.17's own real, 17-column `NeoEpitopeFusion` schema (checked directly in `hmf-common`) has no `copyNumber` field, but NEO v1.3's own reader (checked out at the real `neo-v1.3` tag) unconditionally expects one. Checked every tagged LINX release through the current latest, v2.3, and confirmed **none** of them write this field -- only the current, unreleased `hmftools` `master` branch does, meaning no real, installable LINX release satisfies what NEO v1.3 expects for fusion-derived neoepitopes at all right now. Rather than fabricate the missing column, `_hmftools_linx_neo_epitopes`'s `output:` was reverted to the real underscore-named file LINX actually writes (`<sample>.linx.neo_epitope.tsv`) and the compat symlink removed -- the rule still produces real, useful LINX fusion-neoepitope data, it's just no longer wired to satisfy NEO's specific (currently unsatisfiable) expectation. `modules/neo/1.0` now skips fusion-derived neoepitopes by default until a real LINX release closes this gap -- see that module's own `CHANGELOG.md`.
- Removed `_hmftools_linx_neo_epitopes` from `_hmftools_all`'s own default target list (found on a real run: it was still being triggered, rerunning LINX a second time, for output nothing downstream actually reads any more after the fix above -- `_hmftools_all`'s own target list was never updated when the rule stopped being consumed). The rule itself is unchanged and still runs correctly if requested directly (`rules._hmftools_linx_neo_epitopes.output.neo_epitopes`); it's just no longer part of the default `_hmftools_all` set.

## [1.0] - 2020-07-29

This release was authored by Laura Hilton.
- This module takes output from the `gridss` module to perform purity/ploidy/CNV calling (PURPLE) and generate SV plots (LINX). 
- Is able to run in unmatched normal mode, but the results will be substantially noisier than on matched samples. 
- For optimal pipeline efficiency, include both `modules/gridss/1.0/gridss.smk` and `modules/hmftools/1.0.smk` in the same Snakefile, with `_hmftools_all` as the target rule.
