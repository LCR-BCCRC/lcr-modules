## [1.0] - 2026-09-21

This release was authored by Ryan Morin.

- Added a standalone Level 2 module wrapping TRUST4 ([liulab-dfci/TRUST4](https://github.com/liulab-dfci/TRUST4)) for BCR/TCR immune-repertoire reconstruction from bulk RNA-seq, as the RNA-side complement to this repo's existing DNA-side immunogenomics modules (`pvactools`, `mhc_hammer`, `lilac`). Bulk RNA-seq only: no raw-FASTQ input mode, no barcode/UMI/10x single-cell support (see README "What's not included in v1"). No tumour/normal pairing concept anywhere -- TRUST4 operates on one BAM per `sample_id`, mirrors `modules/star/1.4`'s own `pairing_config.mrna` exactly (`run_paired_tumours: False, run_unpaired_tumours_with: "no_normal", run_paired_tumours_as_unpaired: True`) so every RNA-seq sample is its own independent unit.
- **Depends on `modules/star/1.4`**: `inputs.sample_bam`/`inputs.sample_bai` default to that module's own final coordinate-sorted + duplicate-marked BAM output (`_star_output_bam`, `99-outputs/bam/{seq_type}--{genome_build}/{sample_id}.bam`). Any coordinate-sorted, indexed RNA-seq BAM works -- TRUST4 has no hard STAR dependency, just a real need for genuine genome coordinates to extract candidate reads from.
- **bioconda-installable, no licensing gate** (`trust4=1.1.10`) -- unlike `mhc_hammer`'s Novoalign/HLA-HD/VEP, this is a completely normal `conda_envs`/`container_envs` entry, no user-supplied external script directory needed. Confirmed via a real local `mamba create -n test-trust4 -c bioconda -c conda-forge trust4=1.1.10` install (2026-09) that `run-trust4` and its sibling compiled binaries (`bam-extractor`/`trust4`/`annotator`) all land in the same env `bin/`, so calling `run-trust4` on `PATH` works with no path plumbing.
- **Reference files downloaded automatically, pinned to a specific commit for reproducibility**: TRUST4's own GitHub repo ships small (200-350KB), pre-built, plain-text `hg19_bcrtcr.fa`/`hg38_bcrtcr.fa` (genome-build-specific V/D/J/C gene coordinates) and `human_IMGT+C.fa` (species-only IMGT reference) directly in-repo -- no manual `BuildDatabaseFa.pl`/`BuildImgtAnnot.pl` build step needed for standard human builds. `_trust4_download_bcrtcr`/`_trust4_download_imgt` fetch these from `raw.githubusercontent.com/liulab-dfci/TRUST4/<commit>/...` (`options.trust4_repo_commit`, currently pinned to `4032f90b82b3cca6d56aaa7645cc7ee51dd3889c`), mirroring this repo's own established pinned-commit-download convention (`modules/vcf2maf/1.3/vcf2maf.smk`'s `_vcf2maf_gamblr_config`, `modules/lymphgen/2.1/lymphgen.smk`'s equivalent -- bare `wget -qO`, no checksum verification, this repo's real accepted norm for a small pinned-commit file). `options.trust4_bcrtcr_map` (genome_build -> which `*_bcrtcr.fa` to use) mirrors `modules/pvactools/1.0`'s own `VEP_ASSEMBLY_MAP` pattern exactly, including the same defensive assert-with-actionable-message guard at parse time if a samples-table genome_build isn't covered.
- **`--repseq` defaults off** (`options.repseq`): confirmed by reading `run-trust4`'s own source that this flag internally maps to `--trimLevel 2 --skipMateExtension`, intended for dedicated, non-UMI bulk TCR-seq/BCR-seq capture libraries -- not this module's primary use case (generic bulk tumour RNA-seq), where mate-pair extension genuinely helps recover more complete contigs given how much sparser on-target VDJ coverage is compared to a dedicated capture library. Exposed as a real option for anyone feeding genuine repseq-capture data through this module later.
- **`--clean 1` used instead of manual `temp()` bookkeeping**: confirmed directly (reading `run-trust4`'s own source, then a real local run against TRUST4's own bundled `example.bam`) that this built-in TRUST4 flag deletes its own intermediate files (`*_toassemble*`, `*_assembled_reads.fa`, `*_final.out`, `*_raw.out`, `*_airr_align.tsv`) after a successful run -- the real run's output directory afterward contained exactly `*_report.tsv`/`*_cdr3.out`/`*_annot.fa`/`*_airr.tsv` and nothing else. This means `_trust4_run` never declares those intermediates as Snakemake outputs at all (no `temp()` needed), a real simplification versus `mhc_hammer`'s own hand-audited `temp()` pass (which needed careful per-file verification since nothing upstream cleaned those up itself).
- **Four final per-sample outputs exposed** in `99-outputs/`: `report/{seq_type}--{genome_build}/{sample_id}.trust4_report.tsv` (main CDR3+V/D/J/C+frequency summary), `cdr3/.../{sample_id}.trust4_cdr3.out` (per-consensus CDR1/2/3+gene detail), `annot/.../{sample_id}.trust4_annot.fa` (annotated consensus assembly), `airr/.../{sample_id}.trust4_airr.tsv` (AIRR format, for cross-tool compatibility e.g. VDJTools/Immunarch) -- one small symlink rule per output type, matching this repo's established one-rule-per-output-type convention.
- Verified via a real, minimal dry-run harness (synthetic 2-sample table, one `hg38` and one `grch37` sample) that the DAG resolves correctly (16 jobs: 2× `_trust4_download_bcrtcr` -- one per distinct genome build -- 1× cohort-wide `_trust4_download_imgt`, 2× each of `_trust4_input_bam`/`_trust4_run`/the four `_trust4_output_*` rules), that the rendered `run-trust4` command is correct for both builds, and that the `trust4_bcrtcr_map` assertion fires with a clear, actionable message on an unrecognized genome build (tested with a synthetic `mm10` sample).
- **Real `AmbiguousRuleException` found and fixed via a real dry-run of `demo/run_trust4.smk`** (added this same release -- see below): `_trust4_input_bam`'s original `bai` output (`{sample_id}.bam.bai`) collided with `modules/utils/2.1`'s own completely generic `_utils_bam_index` rule (`{out_dir}/{prefix}/{suffix}.bam.bai`, no constraints at all) the moment both modules were included in the same Snakefile -- which any real trust4 deployment must do, since `modules/star/1.4` (trust4's own default upstream) itself requires `modules/utils` for its sort/markdups/index steps but doesn't include it internally. Same class of bug `modules/mhc_hammer/1.0`'s own CHANGELOG already documents for `_mhc_hammer_novoalign_postprocess`'s `bai`, including that module's own conclusion that a `ruleorder` guard is unreliable (requires both rules to exist at parse time, no way to know if an arbitrary outer Snakefile loads `modules/utils`). Fixed by renaming the tracked output to `{sample_id}.bai` (dropping the `.bam` infix) -- htslib/samtools accept both `{bam}.bam.bai` and `{bam}.bai` as valid index-sidecar names for a file named `{bam}.bam`, so this avoids the pattern collision entirely with no functional downside. Re-verified with a real dry-run afterward: the ambiguity is gone.
- Added `demo/run_trust4.smk` + `demo/trust4_config.yaml`, a standalone single-module demo runner (mirrors `demo/run_sage.smk`'s own shape) chaining `modules/utils/2.1` -> `modules/star/1.4` -> `trust4` against the TCRBOA7 demo mrna FASTQs. Confirmed via a real dry-run that this module's own DAG resolves correctly once chained behind a real `star` alignment (the AmbiguousRuleException above was caught this way); full end-to-end dry-run completion is currently blocked by a pre-existing, environment-specific `workflows/reference_files/2.4` chromosome-provider issue in this local checkout (confirmed unrelated to trust4 by reproducing the identical failure mode on the already-existing, unmodified `demo/mrna_Snakefile.smk`) -- not something to fix as part of this module.
- **Real production crash fixed in `_trust4_input_bam`**: on the very first real cluster run (a real `00-23442_tumorB` sample), `bam-extractor` crashed with `[bam_header_read] invalid BAM binary header (this is not a BAM file). Can not open ...`. Root-caused (and confirmed, not just inferred) that `inputs.sample_bam` for this sample was genuine CRAM content stored/symlinked with a `.bam` name -- the same real-world storage convention `modules/mhc_hammer/1.0`'s own `_mhc_hammer_input_bam` already documents hitting for DNA BAMs. Read the `Makefile` directly to confirm `bam-extractor` links against the *bundled*, ancient `samtools-0.1.19`'s own `libbam.a` (not htslib), which predates CRAM entirely -- unlike `mhc_hammer`'s own downstream tools (real htslib `samtools`, which content-sniffs correctly regardless of extension, so that module's own fix was purely about index-sidecar naming), no amount of correct sidecar naming fixes this for TRUST4: `bam-extractor` structurally cannot parse CRAM, full stop. Fixed by having `_trust4_input_bam` always re-encode through `samtools view -b -T <genome_fasta>` (resolved via `reference_files()` for the sample's own `{genome_build}`, matching `modules/mhc_hammer/1.0`'s own `_mhc_hammer_vep_annotate` idiom) rather than symlinking -- a real htslib tool content-sniffs correctly, so this transparently handles both a genuinely-already-BAM input (a harmless re-encode) and a CRAM-disguised-as-`.bam` input (the real fix) with no runtime format-detection logic needed. `-T` is passed unconditionally rather than relying on CRAM's own automatic `REF_CACHE`/URL-based reference resolution, since `mhc_hammer`'s own CHANGELOG already documents that silently degrading into per-sequence network fetches from EBI's ENA CRAM registry on a real cluster run. `inputs.sample_bai` is no longer needed at all -- a plain, non-region-restricted `samtools view -b` conversion doesn't need an index, and this rule now indexes its own freshly-encoded output directly. This rule is no longer a `localrule` (real, potentially large I/O now, not an instant symlink) and gained real `threads`/`resources` (`options.threads.input_bam`/`options.resources.input_bam`, 8 threads/8000MB, matching `modules/star/1.4`'s own samtools-based sort/index allocation).
- **Verified for real, not just by reasoning about it**: reproduced the exact production error locally by round-tripping a real BAM through `samtools view -C` to produce genuine CRAM content named `.bam`, then feeding it directly to the real `bam-extractor` binary -- got the identical error message verbatim (`[bam_header_read] invalid BAM binary header (this is not a BAM file)`). Then ran the actual fix command (`samtools view -b -T ref.fa ...`) against that same disguised-CRAM file and re-fed the *result* to `bam-extractor`: it got fully past header parsing and into real read extraction, confirming the fix resolves the exact real failure mode end-to-end, not just in theory.
