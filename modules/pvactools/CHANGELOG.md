## [1.0] - 2026-09-09

This release was authored by Ryan Morin.

- Added a standalone module wrapping pVACtools' `pvacseq` for DNA-based neoantigen prediction, as an alternative to `modules/neo/1.0` (HMF Tools' NEO) -- both modules coexist, `neo`'s own fate not decided as part of this work. pVACseq only (not pVACfuse/pVACbind/pVACvector); DNA-only (no RNA-seq expression/coverage integration), matching this repo's own `lilac`/`mhc_hammer`/`neo` DNA-first precedent; Class I + Class II support.
- **Variant source is `vcf2maf`, not any specific caller/PURPLE.** An earlier design sourced somatic variants from `modules/hmftools/1.1`'s own PURPLE somatic VCF directly (the same anchor `neo` uses) -- revised after discussion: reading `modules/vcf2maf/1.3`'s own tracked, symlinked raw VCF (`_vcf2maf_input_vcf`'s output) instead means this module inherits `vcf2maf`'s own already-generic, caller-agnostic `inputs.sample_vcf_gz` for free, and never needs to reach into any specific variant-calling module. `modules/hmftools/1.1`/PURPLE is not a dependency of this module at all.
- **`_pvactools_extract_coding_regions`/`_pvactools_subset_to_coding_variants`** reuse `vcf2maf`'s own final MAF `Variant_Classification` column (already computed by its earlier VEP run) to subset the raw VCF down to only protein-altering positions (`Missense_Mutation`, `Nonsense_Mutation`, `Frame_Shift_Ins`/`Del`, `In_Frame_Ins`/`Del`, `Nonstop_Mutation`, `Translation_Start_Site` -- `Splice_Site` deliberately excluded, since splice-derived neoepitopes are pVACsplice's job, out of scope for this pVACseq-only module) before this module's own dedicated VEP+Frameshift+Wildtype annotation. Motivation: a WGS sample carries far more variants than WES/capture, and the large majority are already known (from `vcf2maf`'s own earlier VEP run) to be silent/non-coding and structurally incapable of producing a neoantigen -- re-annotating and binding-predicting all of them via pvacseq's own multi-algorithm scoring (the genuinely expensive step in this pipeline) would be pure waste. Position-only matching (`Start_Position`/`End_Position` +/-1bp padding via `bcftools view -R`), not exact ref/alt, to tolerate MAF/VCF indel-representation differences -- confirmed working end-to-end on a real synthetic VCF+MAF pair (correctly kept a `Missense_Mutation`/`Frame_Shift_Del` pair, correctly dropped `Silent`/`Intron`/`5'UTR`), but not yet independently verified to never drop a real candidate at a genuinely multiallelic/decomposed site on real data.
- **Considered and rejected reusing `vcf2maf`'s own "annotated VEP VCF" output directly** (`_vcf2maf_run`'s `output.vep`), which would have avoided a second VEP invocation entirely. Confirmed by reading `modules/vcf2maf/1.3/vcf2maf.smk` directly: that output is a dead placeholder -- declared, but the shell command never asks `vcf2maf.pl` to write it (the last line is a bare `touch {output.vep}`), and even if it were real, the underlying `vcf2maf.pl` invocation never requests the `Frameshift`/`Wildtype` plugins pvacseq specifically requires. This module's own separate VEP annotation step (`_pvactools_vep_annotate`) is not avoidable.
- Direct `vep` invocation (not through any wrapper), mirroring `modules/mhc_hammer/1.0`'s own `_mhc_hammer_detect_muts` convention exactly (`options.vep_path` exported onto `PATH`, `container: None`) rather than `modules/vcf2maf/1.3`'s wrapper-script convention, since this module needs specific plugin flags VEP itself must receive directly. `_pvactools_install_vep_plugins` (`pvacseq install_vep_plugin <dir>`) is a genuinely new pattern in this repo (confirmed via a repo-wide grep for "install_vep_plugin"/"VEP_plugins": zero prior hits) -- modeled on `modules/lilac/1.0`'s own `_lilac_download_ensembl_cache` (module auto-fetches its own support data). Confirmed via a real local install (pvactools=7.1.3, pip): output is exactly `Frameshift.pm`/`Wildtype.pm`, flat, no nesting.
- **Real regression caught via a real dry-run before this was ever deployed**: `_pvactools_vep_annotate` originally depended on `_pvactools_install_vep_plugins`'s bare `plugins_dir` directory output. `op.setup_module()` pre-creates every declared subdirectory empty upfront, so Snakemake saw that (empty) directory as "already existing" and never scheduled the job that actually populates it with the two real plugin files -- confirmed missing entirely from a full-chain dry-run's own job list, then confirmed present when the same rule was dry-run in isolation (ruling out a config error). Fixed by depending on the two real files (`frameshift`/`wildtype` outputs) directly instead of the bare directory, deriving the actual `--dir_plugins` directory path from one of them via `os.path.dirname()`. The same class of bug already motivated `_pvactools_run`'s own `directory()` output being paired with a `touch()`-ed `complete` sentinel that every downstream output rule also depends on.
- HLA allele-list construction (`_pvactools_prepare_allele_list`/`src/prepare_allele_list.py`) combines `modules/lilac/1.0`'s own Class I typing (`.lilac.tsv`'s `Allele` column, confirmed via `HlaAllele.toString()` in hmftools source to already be bare `A*02:01`-style, no `HLA-` prefix -- prefixed here) with `modules/mhc_hammer/1.0`'s own Class II HLA-HD typing (`hla2_alleles.csv`, optional, existence-gated the same way `modules/lilac/1.0`'s own `gene_copy_number`/`somatic_vcf` inputs are). Real allele-naming conventions confirmed against a real installed pvactools=7.1.3 (`pvactools valid_alleles`): Class I needs the `HLA-` prefix (`HLA-A*02:01`), Class II single-chain genes (`DRB1`/etc.) do not (`DRB1*01:01`), and `DQA1`/`DQB1` and `DPA1`/`DPB1` heterodimers are submitted as hyphenated pairwise combinations (`DQA1*01:01-DQB1*02:01`) -- confirmed exact format/separator directly from `valid_alleles` output, not assumed. `HLA-DM`/`HLA-DO` genes are excluded entirely (non-classical peptide-loading chaperones, never presented to T cells -- not relevant to neoantigen prediction, and pvacseq has no alleles for them). Homozygous/duplicate alleles are deduplicated before the final comma-separated list (binding prediction is allele-intrinsic; a duplicate only costs runtime), with an audit TSV recording every raw-to-resolved mapping (including skipped "not typed"/non-classical entries) for QC visibility. Verified end-to-end against synthetic fixtures covering heterozygous/homozygous Class I, homozygous Class II single-chain, DQ/DP pairing, "not typed" skipping, non-classical-gene exclusion, Class-I-only fallback, and the both-classes-empty error path.
- Real, confirmed `pvacseq run` CLI facts (pvactools=7.1.3, checked directly via `pvacseq run --help` against a real local install, not just documentation): a single invocation mixes Class I + II alleles/algorithms together, auto-splitting results into its own `MHC_Class_I`/`MHC_Class_II` output subdirectories -- no need for two separate rules. **There is no short `-n` flag for the normal sample name** -- only `--normal-sample-name` (an earlier draft of this rule assumed a `-n` flag existed, based on general docs skimming; caught and fixed before implementation via the real CLI check, not discovered as a runtime failure). `-e1`/`-e2`/`-b`/`-m`/`-t`/`--iedb-install-directory` all confirmed to exist with the expected real defaults (`[8,9,10,11]`/`[12..18]`/`500`/`median`).
- Real, confirmed packaging gotcha (pvactools=7.1.3, 2026-09, checked via a real local pip install): `mhcflurry-downloads` imports the deprecated `pkg_resources` API (`from pkg_resources import resource_string`), which modern `setuptools` (81+) no longer ships at all -- the same warning the tool itself prints even names the deprecation date (2025-11-30) as already past. Confirmed on a real install that `ModuleNotFoundError: No module named 'pkg_resources'` occurs with setuptools 84, and that pinning `setuptools<81` fixes it (`mhcflurry-downloads --help`/`info` both work after the pin). `envs/pvactools/pvactools-7.1.3.yaml` pins this explicitly. Also confirmed via a real `mhcflurry-downloads fetch` attempt: pointing `MHCFLURRY_DOWNLOADS_DIR` at a fresh/custom directory disables mhcflurry's own default-release auto-detection (`RuntimeError: No release defined`) -- `--release 2.0.0` (the real current default, confirmed via `mhcflurry-downloads info`) must be passed explicitly; `_pvactools_download_mhcflurry_models` does this via `options.mhcflurry_release`.
- Confirmed via a real local install that `MHCnuggetsI`/`MHCnuggetsII` need no equivalent download step at all -- their trained models ship bundled directly in the package (`mhcnuggets/saves/production/*.h5`).
- Confirmed `pvactools=7.1.3` is available via bioconda (checked via `mamba search`), matching this repo's general preference for conda over pip. Its own bioconda recipe pulls in `vaxrank`→`shellinford`, a Linux-only native dependency (confirmed absent for osx-arm64) -- consistent with pVACtools' own documented "Linux only" requirement, so this doesn't block the real cluster deployment target, but does mean the conda environment itself could not be created/tested end-to-end on this session's own (macOS) development machine. CLI/packaging verification above was instead done via a separate `pip install` into a real `python=3.11` virtualenv (pVACtools requires Python 3.9-3.11; the machine's own default Python was 3.13, too new).
- `_pvactools_subset_to_coding_variants` also reheaders the subsetted VCF's `#CHROM` sample columns to guarantee they equal `wildcards.tumour_id`/`normal_id` literally, defensively handling both a raw caller VCF (its own original sample names) and a VCF already normalized to `vcf2maf`'s own `TUMOR`/`NORMAL` convention (`modules/vcf2maf/1.3`'s own `_vcf2maf_run` does the reverse rename, confirmed by reading its shell script directly) -- pvacseq's own `sample_name`/`--normal-sample-name` arguments require an exact match to a real column name in the VCF's own `#CHROM` line. A raw VCF using some third, unrelated sample-naming convention would not be caught by this defensive check -- not yet independently verified against a real `vcf2maf` deployment.
- `_pvactools_extract_coding_regions`/`_pvactools_prepare_allele_list`'s own Python scripts (`src/maf_coding_positions.py`/`src/prepare_allele_list.py`) are invoked via `shell: python3 {input.script} ...` with explicit argparse-style CLI arguments, matching `modules/mhc_hammer/1.0`'s own convention for module-owned scripts (e.g. `src/parse_hlahd_output.R`), not Snakemake's `script:` directive.
- Neither `_pvactools_subset_to_coding_variants`'s nor `_pvactools_vep_annotate`'s own output is a permanent module artifact -- both are `temp()`-marked, following the checkpoint-placement lesson learned this session for `modules/mhc_hammer/1.0`'s own `temp()` pass: each has exactly one downstream consumer and is cheap/fast to regenerate (a small, already-coding-filtered variant set; VEP annotation of it is not the expensive step in this pipeline -- pvacseq's own multi-algorithm binding prediction is), so `temp()`-marking them is safe and avoids leaving redundant intermediate VCF copies on disk indefinitely.
- Exact final `pvacseq` output filenames/directory structure (`MHC_Class_I/<sample>.filtered.tsv` etc.) are **placeholders**, based on general pVACtools documentation knowledge, not confirmed against a real run's actual output directory in this session. The four output-symlinking rules are written defensively (symlink if the expected file exists, otherwise touch an empty placeholder and print a warning) specifically so a filename mismatch on the first real run doesn't hard-fail the whole pipeline -- correct the path once confirmed via a real `ls -R`, rather than guessing twice.
- Full end-to-end DAG structure verified via a real (non-mocked) local dry-run: a minimal standalone test Snakefile with hand-placed stub `vcf2maf`/`lilac` input files, confirming all 12 expected jobs (`_pvactools_download_mhcflurry_models` through `_pvactools_all`) plan correctly with no errors. `_pvactools_extract_coding_regions` and `_pvactools_prepare_allele_list` (the two pure-Python localrules) were additionally executed for real (not just dry-run) against synthetic fixtures, confirming their actual shell invocations and output content are correct, not just their planned DAG shape. `_pvactools_subset_to_coding_variants`'s own `bcftools view -R` + reheadering-`awk` + `bgzip`/`tabix` shell logic was also run for real (outside Snakemake, using the exact same command template) against a synthetic VCF, confirming it correctly keeps/drops the expected records.
- **Not yet independently verified** (same honesty standard as `neo`'s own CHANGELOG): whether `pvacseq run` accepts a bgzipped+tabixed VCF or needs a plain `.vcf`; HLA-HD's raw allele string format inside `hla2_alleles.csv` (field count, gene-prefix presence); whether position-only MAF→VCF matching ever silently drops a real candidate at a multiallelic/decomposed site on real data; the full IEDB-gated algorithm name list used for the parse-time opt-in assertion (only `NetMHCpan`/`NetMHCIIpan` confirmed IEDB-mediated, the rest of `options.iedb_gated_algorithms` is inferred); minimum/maximum Ensembl VEP version pVACtools' plugins require. All real `pvacseq`-conda-env-dependent rules (`_pvactools_install_vep_plugins`, `_pvactools_download_mhcflurry_models`, `_pvactools_vep_annotate`, `_pvactools_run`) are structurally verified (dry-run DAG shape, real CLI flags/behaviour checked via a separate pip install) but not yet executed for real through this module's own conda environment end-to-end -- do that (plus a real `vcf2maf`+`lilac`+`mhc_hammer` chain, per this module's own README/verification plan) before trusting this in production.
- **Class I HLA typing switched from `modules/lilac/1.0` to `modules/mhc_hammer/1.0` for both classes.** The original design used LILAC for Class I (`inputs.lilac_tsv`) alongside mhc_hammer for Class II, mirroring the split the two modules' own scopes suggested (LILAC is class-I-only). Revised after a direct question about it: mhc_hammer already produces its own Class I typing (`_mhc_hammer_output_hla_final_result`, HLA-HD's consolidated per-patient result), so the split wasn't necessary -- keeping this module to a single upstream typing dependency (mhc_hammer only) was chosen over LILAC's better-documented WGS typing accuracy (LILAC's own README notes it's validated at 30-40x germline/100x tumour WGS depth, while mhc_hammer's HLA-HD-based typing was tuned for WES and "has repeatedly needed depth-filter tuning on WGS data in practice"). `inputs.lilac_tsv` is removed; `inputs.hla_alleles` (required, patient-keyed, resolved via the same `_pvactools_get_patient_id_for_tumour` helper already used for `hla2_alleles`) takes its place. `src/prepare_allele_list.py` now parses HLA-HD's own `{patient_id}_final.result.txt` directly (gene name + two allele columns, tab-delimited, alleles already carrying an `HLA-` prefix per HLA-HD's standard convention) instead of LILAC's `.lilac.tsv`; this exact field layout is based on HLA-HD's well-documented convention, not independently re-verified against a real file in this session, so parsing is deliberately defensive (case-insensitive "not typed" check, tolerates the `HLA-` prefix being present or absent). Re-verified end-to-end (dry-run DAG + a real, non-dry-run execution of `_pvactools_prepare_allele_list`) with an updated synthetic fixture matching this format.
- **Real correctness bug caught and fixed in `inputs.vcf2maf_maf` before this was ever deployed**: an early edit pointed it at `_vcf2maf_output_maf` (vcf2maf's own CrossMap-projected, cohort-wide-`target_build` MAF). `_pvactools_subset_to_coding_variants` matches this MAF's positions directly against `vcf2maf_raw_vcf`'s own coordinates, which are in each sample's *native* `genome_build` -- for any sample whose native build doesn't match the projection target, a CrossMap-projected MAF's coordinates silently don't correspond to the same variants in the raw VCF at all. Fixed by pointing `inputs.vcf2maf_maf` at `_vcf2maf_output_original` instead (confirmed by reading `modules/vcf2maf/1.3/vcf2maf.smk` directly: its own output path is keyed on `{genome_build}` with no `target_build`/`projection` involved at all, matching `vcf2maf_raw_vcf`'s own coordinate system exactly). `README.md`/`src/maf_coding_positions.py`'s own docstring updated to name the correct rule explicitly, since the wrong one is an easy mistake to repeat (same MAF-shaped file, subtly different coordinate system).
- **Real cohort-scale gap caught before a production run over the full sample list**: `_pvactools_all`'s own target-list `expand()` previously requested every matched pair in `CFG["paired_runs"]` unconditionally, including `vcf2maf_raw_vcf`/`vcf2maf_maf`/`hla_alleles` as hard-required inputs with no existence gate. Running over a whole cohort means some pairs will have failed `mhc_hammer` or the upstream SLMS-3/vcf2maf pipeline entirely, so those files genuinely don't exist -- Snakemake would hard-fail the whole invocation with `MissingInputException` on the first such pair rather than processing every pair that does have real input. Not a checkpoint scenario (the candidate pair list is fully known upfront from the sample table; the only question is whether each pair's files already exist) -- fixed with `_pvactools_pair_has_required_inputs`, a new parse-time filter applied to `CFG["paired_runs"]` right after the existing `pair_status == "matched"` narrowing, using the exact same existence-gated pattern already established for the optional `hla2_alleles` input, just applied at the target-list level since these three are hard requirements a pair can't run without at all. Prints an `INFO [pvactools]: skipping N of M pair(s)...` message naming the excluded tumour sample IDs. Verified with a real dry-run in both directions: all pairs present → unchanged job count (no skip message); one pair's `vcf2maf_maf` stub removed → that pair's targets silently drop out of `_pvactools_all`'s own input list (down to 1 total job, just `_pvactools_all` itself) instead of crashing.
- **Real, first-production-run failure #1**: `_pvactools_vep_annotate` failed with `ERROR: Multiple assemblies found for cache version 105 (GRCh38, GRCh37) - specify one using --assembly [assembly]` -- the shared `--dir_cache` in use has both builds cached under the same VEP version, and this rule never passed `--assembly` at all. Fixed by adding `options.vep_assembly_map` (`grch37`/`hs37d5` -> `"GRCh37"`, `hg38` -> `"GRCh38"`) -- mirrors `modules/vcf2maf/1.3`'s own `VCF2MAF_VERSION_MAP` transform (`"grch" -> "GRCh"`) exactly, kept as a separate, user-configurable copy per this repo's established convention -- plus a parse-time assertion (same style as `modules/lilac/1.0`'s own `version_map` check) that every genome_build in the sample table is covered. `_pvactools_vep_annotate` now passes `--assembly {params.assembly}`. Re-verified via dry-run: the rendered shell command includes `--assembly GRCh37` for a `grch37` pair.
- **Real, first-production-run failure #2**: `_pvactools_download_mhcflurry_models` failed with `KeyError: None` inside mhcflurry's own `get_current_release_downloads()`, even with `--release 2.0.0` passed explicitly and the `setuptools<81` pin working correctly (the `pkg_resources` deprecation warning still printed, but import succeeded -- this was a genuinely different, new error). Root-caused by reproducing locally and reading mhcflurry's own `downloads.py` source directly: `configure()` (run once at import) only ever sets the module-global `_CURRENT_RELEASE` -- from `--release`, `MHCFLURRY_DOWNLOADS_CURRENT_RELEASE`, or the package's own default -- **inside** its `if not MHCFLURRY_DOWNLOADS_DIR:` branch. Setting `MHCFLURRY_DOWNLOADS_DIR` to any custom value (exactly what both `_pvactools_download_mhcflurry_models` and `_pvactools_run` were doing) skips that whole block unconditionally, leaving `_CURRENT_RELEASE` permanently `None` regardless of `--release` -- `fetch_subcommand`'s own `get_current_release_downloads()` then does `metadata['releases'][None]`, an unconditional `KeyError` with no environment-variable workaround; this is a real bug in mhcflurry itself (`--release`'s CLI value is disconnected from the actual global state used to look up available downloads), not a usage mistake. Fixed by dropping `MHCFLURRY_DOWNLOADS_DIR` entirely from both rules, letting mhcflurry manage its own default per-user download location (`user_data_dir("mhcflurry", ...)`, typically under `$HOME`). Confirmed this doesn't break `_pvactools_run`'s own later use of the downloaded models: `get_path()`/`get_default_class1_models_dir()` (what pvacseq actually calls at prediction time) only read the resolved `get_downloads_dir()`, never `_CURRENT_RELEASE`, so this only ever affected the `fetch`/`info` CLI subcommands. **Known tradeoff**: mhcflurry's models now live in `$HOME` rather than this module's own results directory, unlike every other reference/resource this repo manages itself -- worth revisiting if `$HOME` quota becomes a real constraint on a given cluster. Reproduced the exact failure in a clean local `python=3.11` + `pip install mhcflurry` environment before fixing, confirming it's a real mhcflurry bug and not an artifact of the bioconda packaging or this module's own env YAML.
- **First real, fully-completed pvacseq run** (pvactools=7.1.3, real DLBCL capture pair, 2026-09-09) confirmed both fixes above work end to end, and resolved the last major open item -- exact output filenames. Real `MHC_Class_I`/`MHC_Class_II` filenames are `{tumour_id}.MHC_I.filtered.tsv`/`{tumour_id}.MHC_I.all_epitopes.tsv` (and `.MHC_II.` for class II) -- an earlier draft guessed `{tumour_id}.filtered.tsv`/`{tumour_id}.all_epitopes.tsv` with no class infix at all, which would have silently hit every output rule's defensive empty-placeholder-and-warn path instead of symlinking the real file. Fixed all four existing output rules with the real names. Also discovered a third, previously unaccounted-for `combined/` directory (`{tumour_id}.Combined.filtered.tsv`/`.all_epitopes.tsv`) merging both classes into one report -- likely the single most useful deliverable for most downstream analysis, since it avoids concatenating `MHC_Class_I`/`MHC_Class_II` by hand. Added `_pvactools_output_combined_filtered`/`_pvactools_output_combined_all_epitopes` (same defensive symlink-or-placeholder pattern) and included both in `_pvactools_all`'s own target list. Not yet exposed: pvacseq's own `.all_epitopes.aggregated.tsv`/`.aggregated.metrics.json` reports (its documented tiered/prioritized candidate view, generated per class and for `combined/` alike) -- worth adding as a follow-up if the flat filtered/all_epitopes tables turn out to be less useful in practice than the tiered aggregate view. Real wall-clock timing from this run's own file timestamps (one pair, all 4 ungated algorithms, both classes, `-t 8`): `MHC_Class_I` ~3 min, `MHC_Class_II` ~3-4 min, `combined` ~1 min -- **~8 minutes total** for `_pvactools_run` on this pair. Re-verified DAG shape via dry-run after adding the two new rules (14 total jobs, up from 12).
- **Added `_pvactools_apply_additional_filter`**, running `pvacseq binding_filter` with a few standard, configurable threshold presets (`options.additional_filters`) against the already-computed combined `all_epitopes.tsv`, producing `99-outputs/additional_filters/{preset}/*.filtered.tsv` for each. Motivated directly by the observation above (several samples' default `filtered.tsv` came back empty/near-empty) -- `binding_filter` is pure post-processing on already-computed scores (confirmed by reading `pvactools/lib/binding_filter.py` directly: no model/IEDB calls at all, just re-applies thresholds to an existing report), so generating several differently-thresholded views costs essentially nothing beyond the primary `pvacseq run` itself, and needs no re-computation. Localrule (fast TSV post-processing), one job per pair per preset via a cross-product `expand()` (every pair gets every preset, using the standard `expand(expand(..., zip, ..., allow_missing=True), preset_dim=[...])` idiom).
- **Real bug caught before shipping, via an actual `pvacseq binding_filter` test run (not just reading the source)**: the initial preset design included two `--percentile-threshold-strategy exploratory` presets (`exploratory`, `permissive`), intended as looser alternatives to pvacseq's own default `conservative` strategy. Confirmed via a real test against a synthetic `all_epitopes.tsv` that `exploratory` is a **silent no-op for our algorithm selection**: `BindingFilter.execute()` only excludes a row under `exploratory` if it fails all four criteria (binding score/binding percentile/presentation percentile/immunogenicity percentile) simultaneously (`if all(filters): continue`), but immunogenicity percentile is always `'NA'` for us (none of `MHCflurry`/`MHCflurryEL`/`MHCnuggetsI`/`MHCnuggetsII` compute it -- that needs `DeepImmuno`/`ImmuScope_IM`, which we don't run), and pvactools' own `Filter.execute()` treats `'NA'` as automatically not-failing -- so that one permanently-`NA` column alone guarantees `all(filters)` can never be `True`, meaning every row survives regardless of how poor its other three scores are. Verified directly: a synthetic row failing all three real criteria (IC50 1000 > 500, percentile 5.0 > 2.0, presentation 5.0 > 2.0) still passed `exploratory` filtering unchanged -- confirmed `conservative` strategy correctly excluded the same row in the same test. Both presets replaced with `relaxed`/`very_relaxed` (both `conservative` strategy, varying only the numeric cutoffs) -- `exploratory` would become meaningful again if `DeepImmuno`/`ImmuScope_IM` are ever added to `options.prediction_algorithms`, noted directly in `default.yaml`'s own comment for whoever revisits this.
- **Grouped `_pvactools_subset_to_coding_variants`/`_pvactools_vep_annotate`/`_pvactools_run` into a single cluster job** (`group: "vep_and_run"`) -- real, requested change: both of the first two rules finish in well under a minute on real data, and the target cluster penalizes total job *count*, not just aggregate compute time, so several short jobs per pair add up. Mirrors an already-established convention in this repo (`modules/freebayes/1.0`'s own `"input_and_run"`/`"normalize_and_bgzip"` groups) rather than inventing a new pattern. Verified for real (not just parsed without error) via `snakemake -n --cluster echo --jobs N`, which is the only way to see Snakemake's own group-job planning in a dry-run -- confirmed a single `group job vep_and_run` containing all three rules per pair. **Real tradeoff, flagged directly in the rule comments**: Snakemake's group resource aggregation sums every member rule's `mem_mb`/`threads` rather than assuming sequential execution, so the combined job reserves `2000+8000+16000=26000` mem_mb and `1+4+8=13` threads for the group's whole duration (a few minutes, dominated by `_pvactools_run` itself) -- not just `_pvactools_run`'s own `16000`/`8`. Same class of tradeoff already documented for `modules/mhc_hammer/1.0`'s own grouping consideration earlier this session.
