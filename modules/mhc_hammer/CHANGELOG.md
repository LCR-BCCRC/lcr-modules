# Changelog

All notable changes to the `mhc_hammer` module will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.0] - 2026-07-30

This release was authored by Ryan Morin.

- Ported the DNA analysis arm of MHC Hammer ([McGranahanLab/mhc-hammer](https://github.com/McGranahanLab/mhc-hammer)) to native Snakemake rules, rather than wrapping upstream's Nextflow pipeline. RNA allelic expression/imbalance/repression and alternative splicing are out of scope for this version (see README).
- Novoalign and HLA-HD are user-supplied filesystem paths (`options.novoalign_dir`, `options.hlahd_dir`), not conda/container-managed -- both are gated behind manual, registration/licence-restricted downloads that can't be automated into a build.
- MHC Hammer's own `bin/*.R`/`bin/*.sh` scripts are **not bundled in this module** and never will be: upstream is distributed under a Cancer Research Horizons academic-use licence that prohibits redistribution and modification (see README "Prerequisites"). `options.mhc_hammer_scripts_dir` points at a clone the user obtains and licenses themselves, following the same pattern already used by this repo's `lymphgen`/`dlbclass` modules for similarly-restricted third-party code.
- VEP is user-supplied (`options.vep_path`, `options.vep_cache`), following the `vcf2maf` module's own pattern, to avoid the bioconda/Perl `ensembl-vep` dependency conflicts already documented for that module.
- The MHC/IMGT reference bundle (versioned, non-gated Zenodo download) is fetched and cached by the module itself (`_mhc_hammer_download_reference`).
- Sample grouping uses standard `oncopipe` tumour/normal pairing (`CFG["paired_runs"]`) for WES pair-level rules, plus a custom `patient_id`-wildcarded pattern (mirroring `modules/gridss/2.0/gridss.smk`) for the two per-patient steps (HLA-HD typing, personalised reference construction) that are shared across all of a patient's tumour samples rather than recomputed per run.
- Requires exactly one germline WES sample per patient (errors otherwise) -- a v1 simplification of upstream's behaviour of tolerating multiple germline samples per patient by silently picking one.
- Rule shell commands calling `mhc_hammer_scripts_dir` scripts were cross-checked against a local read-only clone of upstream's `bin/*.R`/`bin/*.sh` (never copied into this repo -- read-only verification only, per the licensing note above). This caught and fixed several real bugs: upstream hardcodes the literal token `wxs` (not a generic seq_type) into filenames several cohort-level R scripts pattern-match on; `make_mutation_table.R` and `make_cohort_overview_table.R` expect to run from a flat directory of bare-basename symlinks to their inputs (mirroring Nextflow's per-task staging) and require a synthesised `inventory.csv`/`hlahd_germline_samples.txt` this module now generates (`_mhc_hammer_generate_inventory`, derived from `CFG["samples"]`/`CFG["paired_runs"]`/`purity_ploidy_file` since lcr-modules has no equivalent of upstream's own samplesheet); `hlahd_parse_output.R` writes into its `--hlahd_folder` argument, requiring an extra move step; `concatenate_dna_analysis_tables.R`'s `--genes` needed to be an unquoted (word-split) argument list, and its output filename didn't match what the module declared.
- Added a separate, parallel HLA class II germline-typing path (`_mhc_hammer_hla2_*` rules, not part of upstream MHC Hammer's own scope) -- types `DRA`/`DRB1`/`DRB3`/`DRB4`/`DRB5`/`DQA1`/`DQB1`/`DPA1`/`DPB1`/`DMA`/`DMB`/`DOA`/`DOB` from each patient's germline sample via HLA-HD (`options.hla2_genes`, region `options.hla2_coords_by_system`). Germline genotyping only -- no personalised reference/Novoalign/CN-AIB/mutation calling for class II. Uses a new module-owned parser (`src/parse_hlahd_output.R`) instead of upstream's `bin/hlahd_parse_output.R`, since that script cross-references a GTF from MHC Hammer's own class-I-only reference bundle to break ties among ambiguous HLA-HD candidates -- no class-II equivalent of that GTF exists, so this parser instead takes HLA-HD's own first-listed (highest-confidence) candidate per allele.
- Added `_mhc_hammer_mutations_to_maf` (`src/mutations_to_maf.R`, module-owned) to postprocess each patient's `{patient_id}_mutations.csv` into a MAF-like table for tools (e.g. `maftools`) that expect MAF input. Since mutations are called against each patient's own personalised, allele-specific reference (one contig per typed HLA allele), there is no genomic coordinate system shared across alleles/samples -- `Chromosome`/`Start_Position`/`End_Position`/`NCBI_Build` are synthetic placeholders, while `Hugo_Symbol`, `Variant_Classification` (derived from a standard VEP SO-term severity-ranked mapping), `Variant_Type`, VCF-to-MAF-trimmed allele calls, VEP annotations, and read counts are all real, derived values. Output: `99-outputs/mutations_maf/{seq_type}--{genome_build}/{patient_id}.mutations.maf`.
- Added `_mhc_hammer_output_hla_final_result`, symlinking HLA-HD's own consolidated class I result file (`{patient_id}_final.result.txt`, already produced inside `_mhc_hammer_hlahd`'s working directory but not previously tracked as its own output) to `99-outputs/hla_alleles/{seq_type}--{genome_build}/{patient_id}.hla_alleles.txt` -- this file uses HLA-HD's own standard IMGT/HLA allele nomenclature, unlike the mhc_hammer-internal personalised-reference contig names (e.g. `hla_a_01_01_01_01`) used in this module's other outputs.
- Fixed `cohort_mhc_hammer_gene_table.csv` being permanently empty regardless of how many times the pipeline was rerun: `_mhc_hammer_mosdepth`'s output had no real consumer anywhere in the DAG (only referenced via an `os.path.exists()` check inside the cohort table's best-effort "completed pairs" filter, not a genuine Snakemake dependency), so it never actually ran, its output file never existed, and every pair was excluded from the cohort table every time. `_mhc_hammer_mosdepth` is now an explicit target of `_mhc_hammer_all`.
- `_mhc_hammer_cohort_table` now strips the `gene == "HLA-NONE"` placeholder row it was staging per-patient (to work around `make_cohort_overview_table.R`'s own unguarded loop crashing on the empty transcriptome allele table this DNA-only module never populates) out of its final output, instead of leaving that artifact for every downstream consumer to filter out themselves.
- `_mhc_hammer_generate_inventory` now only rewrites `inventory.csv`/`hlahd_germline_samples.txt` (and bumps their mtime) when the freshly recomputed content actually differs from what's on disk, instead of unconditionally rewriting them on every invocation.
- `_mhc_hammer_parse_mutations` no longer depends on the shared, cohort-wide `inventory.csv` (which is deliberately regenerated on every invocation) -- it now builds its own tiny, patient-scoped inventory snippet directly from `CFG["paired_runs"]`, since that's all `make_mutation_table.R` actually reads. Removing this dependency edge (not just making the shared file's write content-stable, which turned out not to be enough on its own -- Snakemake cascades a rerun onto every consumer of a rule that's scheduled to run, regardless of whether its output content ends up unchanged) stops `_mhc_hammer_parse_mutations`, and everything downstream of it (`_mhc_hammer_mutations_to_maf`, its outputs), from rerunning for every patient on every single invocation.
- Added diagnostic `INFO` prints to `_mhc_hammer_generate_inventory` showing how many matched pairs currently have a real Battenberg `cellularity_ploidy.txt` file on disk (and an example resolved path), since this rule already runs on every invocation.
- `battenberg_cellularity_ploidy` moved from `options` to `inputs`: it's reference data the module reads (same category as `vep_cache`/`reference_genome_fasta`), not a tool/script path. The `options`/`inputs` split for this specific option caused two separate real bugs in practice (a wrapper script's own config-mutation code targeting the wrong config section, then a user config YAML doing the same) before being moved.
- Fixed a real, intermittent race condition between `_mhc_hammer_hlahd` (class I) and `_mhc_hammer_hla2_hlahd` (class II), confirmed on a real run (`rm: cannot remove '.../hla2/{patient_id}/mapfile': Directory not empty`, failing `_mhc_hammer_hlahd`'s job). `_mhc_hammer_hla2_hlahd`'s output previously lived in a `{patient_id}/hla2/` subdirectory nested inside `_mhc_hammer_hlahd`'s own per-patient workdir -- but `_mhc_hammer_hlahd`'s first shell command is an unconditional `rm -rf` of that entire workdir (needed for a clean retry slate after a partial failure). Since the two rules have no dependency on each other and neither declares the other's files as output, Snakemake could (and did) schedule them concurrently for the same patient, racing `_mhc_hammer_hlahd`'s directory wipe against `_mhc_hammer_hla2_hlahd`'s concurrent writes into the nested `hla2/` subdirectory. Moved class II's output to a sibling `{patient_id}_hla2/` directory instead, making the two rules' workdirs fully disjoint. (The analogous `hla2/` nesting at the preprocessing stage, `_mhc_hammer_hla2_subset_bam` inside `_mhc_hammer_subset_bam`'s per-sample directory, is unaffected and safe: that rule only ever `rm -rf`s its own `{sample_id}_tmpDir`, never the whole per-sample directory.)
- Redesigned how `cohort_mhc_hammer_gene_table.csv` gets built, fixing a real report of it coming back empty whenever a new sample subset was processed. Root cause: the previous design ran upstream's `make_cohort_overview_table.R` exactly once, cohort-wide, with its input list gated by a plain `os.path.exists()` check over `CFG["paired_runs"]` (that current invocation's own sample subset), evaluated once at Snakemake parse time -- so (a) a patient processed under a *different* subset in an earlier invocation was invisible forever (their pair never appeared in the current invocation's own `CFG["paired_runs"]` at all), and (b) even the current subset's own cohort table always looked empty on a first pass, since `os.path.exists()` only ever sees what an *earlier* invocation already finished. Read the entire 749-line `make_cohort_overview_table.R` end to end to confirm every column it computes (including LOH, `dna_aib`, `wxs_fail`) is derived per-patient/per-sample/per-allele -- there is no cohort-wide statistic anywhere -- so the script is safe to split per patient. Added `_mhc_hammer_patient_gene_table` (patient-level, mirroring `_mhc_hammer_parse_mutations`'s own staging/patient-scoped-inventory pattern exactly, but with real Snakemake `input:` dependencies on `dna_analysis`/`patient_dir`/`mosdepth`/`library_size`/`hla_bam_read_count` instead of an existence gate) to run the same unmodified script once per patient, producing a stable `{patient_id}_gene_table.csv` (also exposed at `99-outputs/gene_tables/`) the moment that one patient's own upstream data is ready, independent of any other patient or of which sample subset is currently active. `_mhc_hammer_cohort_table` is now a trivial, module-owned concatenation (pure Python, no R/conda needed) of every `_mhc_hammer_patient_gene_table` output discovered by globbing the filesystem directly -- not by iterating `CFG["paired_runs"]` -- so patients from *any* previously-processed subset are included, not just the current invocation's own. One inherent Snakemake caveat remains, now much narrower than before: `glob.glob()` still runs at DAG-build time, so a patient computed for the very first time in the *same* invocation still needs one more invocation to appear in the combined table -- but nothing already computed is ever forgotten anymore, and no patient's own file depends on any other patient succeeding.
- Fixed `_mhc_hammer_flagstat` failing on samples from one particular `genome_build` (`hg38-nci`), confirmed on a real run (`[W::find_file_url] Failed to read reference "https://www.ebi.ac.uk/ena/cram/md5/..."`, `[E::cram_get_ref] Failed to populate reference`). `_mhc_hammer_input_bam`'s "sample_bam" inputs can be CRAM content symlinked with a `.bam` extension (see that rule's own dual `.bam`/`.cram` naming) -- without a local reference, htslib falls back to fetching each reference sequence one at a time from EBI's ENA CRAM registry over the network, which this cluster can't reach. `_mhc_hammer_build_ref_cache`/`REF_CACHE` already exists for exactly this reason (its own comment already named this exact symptom) but was only ever wired into `_mhc_hammer_subset_bam`/`_mhc_hammer_hla2_subset_bam` -- the only other two rules that read the raw input BAM/CRAM directly -- not into `_mhc_hammer_flagstat`, a third, previously-missed consumer of the same raw file. Fixed by pointing directly at the real local FASTA (simpler and more robust for this rule than depending on the `seq_cache_populate.pl`-built MD5 cache, whose own comment already flagged its output layout as not independently verified) rather than adding the `REF_CACHE` dependency too -- though not with a uniform `--reference` flag: a real run showed `samtools flagstat --reference <fasta>` just prints flagstat's own usage text and fails, since (confirmed directly) `samtools flagstat` has no `-T`/`--reference` flag at all, unlike `samtools view` -- flagstat only accepts the generic `--input-fmt-option reference=<fasta>` mechanism. Verified both forms by building a real minimal CRAM locally and running each command against it directly.
- Fixed a real regression the cohort-table redesign above introduced: restricting a later invocation's `CFG["samples"]` to a different subset (e.g. genomes only, dropping all capture samples) crashed the whole DAG build with `AssertionError: Expected exactly one germline WES sample for patient 'X' (capture--...), found 0` -- confirmed on a real run. Root cause: `_mhc_hammer_cohort_table` declared its glob-discovered per-patient gene table paths as a real Snakemake `input:` list; for any such file left over from an *older* invocation whose `{seq_type}--{genome_build}--{patient_id}` combination the current `CFG["samples"]` no longer contains at all, Snakemake still tries to trace that path's production lineage back through `_mhc_hammer_patient_gene_table` to check staleness, re-evaluating that rule's own input/param functions (including the germline-sample lookup) against the *current*, now-mismatched sample table. Fixed by no longer declaring the glob results as a tracked `input:` at all -- read as plain files inside the `run:` block instead, forced to re-glob fresh on every invocation via `_mhc_hammer_invocation_marker` (the same "always rerun, read whatever's on disk right now" sentinel `_mhc_hammer_generate_inventory` already uses). Verified with a real (non-dry-run) execution: an orphaned capture-build gene table for a patient no longer in a genome-only sample set no longer crashes the DAG build, and its data still correctly appears in the combined cohort table.
- Added `priority:` to the 16 non-localrule rules spanning `_mhc_hammer_flagstat`/`_mhc_hammer_subset_bam` through `_mhc_hammer_parse_mutations`/`_mhc_hammer_patient_gene_table` (monotonically increasing with DAG depth: 10 for the earliest preprocessing rules, up to 90 for the last stage), in response to a real user report of running out of shared scratch disk space when launching many samples at once on a cluster: with no explicit priority anywhere in this file, Snakemake's default scheduler has no reason to prefer advancing a sample already partway through this module's long per-sample chain over starting a brand-new sample's own early, disk-heavy stages, so a large batch launch tends to spread thin across many samples' upstream steps simultaneously rather than carrying already-started samples through to completion. This alone doesn't free any disk (no rule in this chain is `temp()`-marked except `_mhc_hammer_novoalign`'s own raw BAM), but it biases job selection toward finishing in-progress samples first, which is a prerequisite for any future `temp()`-based cleanup to actually keep peak concurrent disk usage down rather than just deferring it. Considered (and deferred, after checking the real numbers) `group:`-ing the same rule range per-sample or per-patient to force back-to-back scheduling on one node: patient-level grouping (bundling `_mhc_hammer_hlahd`/`_mhc_hammer_generate_references`, which are genuinely patient-wildcarded and DAG-connected to both a patient's tumour and normal chains, together with both samples' own preprocessing-through-`make_allele_bams` rules) would reserve roughly 92GB `mem_mb` and 49 threads for the whole group's duration, since Snakemake's default group resource aggregation sums across every member rather than assuming sequential execution -- real numbers pulled directly from this module's own `config/default.yaml`, not an estimate. `priority:` alone has no such resource cost, so it's the starting point; grouping (per-sample, ~36GB/22 threads, cheaper than per-patient) remains a real option if priority alone isn't enough.
- Added `temp()` to the 5 declared outputs in the `preprocessing`-through-`make_allele_bams` range that are consumed by exactly one downstream rule and have no other consumer anywhere in this file (confirmed by grepping every reference to each, not assumed): `_mhc_hammer_subset_bam`/`_mhc_hammer_hla2_subset_bam`'s own `bam`/`bai` (each consumed only by their respective `generate_fqs` rule -- their sibling `read_counts` output is a small, standalone QC artifact with no downstream consumer, deliberately left permanent), `_mhc_hammer_generate_fqs`/`_mhc_hammer_hla2_generate_fqs`'s own `fq1`/`fq2` (consumed by `novoalign`, and for the germline sample specifically also by `hlahd`/`hla2_hlahd`), and `_mhc_hammer_novoalign_postprocess`'s own `bam`/`bai` (consumed only by `make_allele_bams`). Checked each candidate rule directly for existing manual cleanup first (per a real user question) -- `subset_bam_opt.sh` (upstream) does clean up its own internal `{sample_id}_tmpDir` on success, and `_mhc_hammer_novoalign_postprocess` already `rm`s two of its own within-rule scratch files -- but in every case that existing cleanup targets different, already-untracked files than the rule's own declared output; none of it was a substitute for `temp()` on the actual outputs marked here. Before applying this, empirically verified (a real, minimal standalone Snakefile reproducing this DAG's exact shape: per-sample preprocessing chain plus a patient-level `hlahd`/`generate_references` step feeding every sample of that patient) a real concern raised during review: adding a new sample for an already-fully-processed patient, after that patient's germline `temp()` files have already been deleted, does *not* force Snakemake to reconstruct them or re-run `hlahd`/`generate_references` -- it correctly recognizes their own outputs are already up to date and only builds the new sample's own (previously-nonexistent) chain. Note this is forward-looking only: samples already run to completion under the old (non-`temp()`) rules still have their old intermediates sitting on disk permanently, since `temp()` only affects cleanup for files produced by *future* invocations -- manually reclaiming that existing backlog for already-completed samples is a separate, deliberate cleanup task.
- Fixed a real regression the `temp()` change above introduced, caught on an actual run (`_mhc_hammer_make_allele_bams` failing with "Could not retrieve index file" on `{sample_id}.hla.rehead.bam`). `_mhc_hammer_make_allele_bams` only ever declared `_mhc_hammer_novoalign_postprocess`'s `bam` output as a real `input:` -- never the sibling `bai` -- even though its own shell script (`make_hla_bams.sh`, upstream) does indexed, region-based `samtools view` calls against that BAM and therefore genuinely needs the `.bai` alongside it. As long as `bai` was never `temp()`-marked this was silently fine, since the file just sat on disk forever regardless of whether Snakemake knew anything depended on it; once marked `temp()`, Snakemake correctly saw *zero* declared consumers for `bai` specifically (only `bam` was ever referenced elsewhere in this file) and deleted it the moment `_mhc_hammer_novoalign_postprocess` itself finished -- before `make_allele_bams` got a chance to run. First attempted fix (declaring `bai = str(rules._mhc_hammer_novoalign_postprocess.output.bai)` as a real, tracked `input:` on `_mhc_hammer_make_allele_bams`, the same fix already used for `neo`/`_hmftools_output_purple_somatic_vcf`'s `.tbi`) surfaced a second real problem on the very next real-cluster invocation: `UnknownRuleException: There is no rule named _utils_bam_index`. `_mhc_hammer_novoalign_postprocess` indexes its own BAM directly (`samtools index` in its own shell block) rather than going through `modules/utils`'s generic `_utils_bam_index` wildcard rule, but that generic rule's own output pattern (`{out_dir}/{prefix}/{suffix}.bam.bai`) still matches this file's path -- so declaring `bai` as a real, requested input made Snakemake need to resolve a producer for it, and it found two candidates whenever both rules exist in the same Snakefile (a real `AmbiguousRuleException`, confirmed via dry-run) or crashed outright wherever `modules/utils` isn't even included in the first place (this module never includes it itself; whether it's present depends entirely on whatever top-level Snakefile happens to also load it -- true for `demo/capture_Snakefile.smk`, false for the user's own leaner production `run_mhc_hammer.smk`, which is what actually crashed). A `ruleorder` guard was considered and rejected: `ruleorder` requires both named rules to exist at parse time, and there's no reliable way from inside this module to detect whether `modules/utils` will end up loaded by an arbitrary outer Snakefile. Settled on the simpler fix instead: leave `bai` permanently on disk (drop the `temp()` wrapper, revert the `input:` declaration entirely) exactly as it always behaved before the `temp()` pass above. This fully avoids both problems -- no tracked input means no producer-resolution ambiguity, and no `temp()` means no premature deletion -- at the cost of one small `.bai` file per sample persisting indefinitely, negligible next to the multi-GB `bam` it indexes (which is still cleaned up via `temp()`). Re-checked the other 4 `temp()`-marked `bai` outputs from the change above (`_mhc_hammer_subset_bam`/`_mhc_hammer_hla2_subset_bam`): both remain safe as `temp()`, since their only consumers (`generate_fqs`/`hla2_generate_fqs`) exclusively use `samtools collate` (a sequential, whole-file read, no index needed, and no `_utils_bam_index` collision risk since neither `bai` is ever declared as a real input anywhere).
- `_mhc_hammer_novoalign`'s own `bam` output (Novoalign's raw alignment, previously `temp()`-marked since before this session) is no longer `temp()`. Real incident on a production run: after the `.bai` regression above, fixing one sample meant deleting `_mhc_hammer_novoalign_postprocess`'s own (corrupted) `bam`/`bai` and rerunning with `--rerun-incomplete` -- but every rule feeding it (`_mhc_hammer_subset_bam`, `_mhc_hammer_generate_fqs`, and `_mhc_hammer_novoalign` itself) was already `temp()`-marked and long since cleaned up (each one's sole consumer had already finished), so Snakemake had no surviving checkpoint anywhere between the original input BAM and `novoalign_postprocess`'s output. The result: a full re-subset, re-fastq, and complete Novoalign realignment from scratch -- the most expensive step in this chain -- to regenerate what should have been a cheap re-run of a few `samtools` bookkeeping commands. Un-`temp()`-ing just this one file (the alignment output, immediately upstream of `novoalign_postprocess`) is the minimal fix: Snakemake only needs a rule's own inputs to exist if that rule's outputs are themselves missing or stale, so as long as this file persists, any future need to redo `novoalign_postprocess` (or anything downstream) never needs to touch `subset_bam`/`generate_fqs`/`novoalign` again, regardless of whether their own `temp()`-marked outputs still exist. `_mhc_hammer_subset_bam`/`_mhc_hammer_generate_fqs` deliberately remain `temp()` -- they're cheap/fast to redo (subsetting, format conversion) and are only ever needed again if this newly-persistent alignment output itself goes missing, a deeper failure mode than the one this fixes.
- Added `_mhc_hammer_patient_completed_samples`, a new per-patient output (`99-outputs/completed_samples/{seq_type}--{genome_build}/{patient_id}.completed_samples.txt`) listing the sample_id of every one of that patient's candidate samples that has reached `_mhc_hammer_make_allele_bams`' own per-sample checkpoint (`hla_bam_read_count.csv`) as of the current invocation. Real requested use case: checking cohort-wide progress (which samples for a given patient are actually done) without an existing file for this -- the closest existing thing, `{patient_id}_gene_table.csv`, doesn't qualify: its own real Snakemake `input:` requires *every* sample configured for that patient to have finished before the rule is even scheduled, so it can never answer "what's done so far" for a still-in-progress patient, and its schema (gene-level QC rows from the externally-supplied `make_cohort_overview_table.R`) isn't a simple sample manifest anyway. Deliberately built as a LIVE/partial snapshot rather than an all-or-nothing final manifest (explicit design choice): each candidate sample_id's completion is checked via a plain `os.path.exists()` inside the rule's own `run:` block, not declared as a real Snakemake `input:` -- declaring them as tracked inputs would force Snakemake to require every one of them to exist before the rule could run at all, exactly the all-or-nothing behaviour this file exists to avoid. Reuses the exact "untracked existence/glob check inside `run:`, forced to re-evaluate every invocation via `_mhc_hammer_invocation_marker`" idiom `_mhc_hammer_generate_inventory`/`_mhc_hammer_cohort_table` already established, including their same `_write_if_changed`-style content-diffing (only bump the output's mtime when its content actually changed, to avoid needlessly cascading reruns into any future downstream consumer under `--rerun-triggers mtime`) and their same documented inherent caveat: this file only reflects whatever's on disk *when the rule runs*, so a sample finishing moments later won't appear until the next invocation re-triggers it. Writes directly into `99-outputs/` rather than this module's usual separate raw-compute-dir-then-symlink two-step for patient-level outputs, since nothing else in this DAG reads this file and adding a new numbered subdirectory to `CFG["dirs"]` would renumber every subdirectory after it -- confirmed via `oncopipe.setup_subdirs()` that `outputs` always keeps a fixed `"99"` regardless of its position in the `subdirectories` list, so a new file living directly under it carries no such risk. Also caught and fixed a real instance of this module's own already-documented CFG-closure gotcha (see the HELPER FUNCTIONS section comment near the top of this file) before it ever ran for real: the rule's `run:` block initially referenced the closed-over module-level `CFG` directly, which would have crashed with `NameError` at actual execution time, since `run:` blocks execute even later than input/param functions -- after `op.cleanup_module(CFG)` at the bottom of this file has already deleted it. Fixed by re-fetching `CFG = config["lcr-modules"]["mhc_hammer"]` inside the `run:` block itself, mirroring `_mhc_hammer_generate_inventory`'s own existing fix for the identical issue. Verified the core completion-detection logic directly against this repo's own `demo/` harness real output tree (real patient `TCRBOA7`, real samples `TCRBOA7-T-WEX`/`TCRBOA7-N-WEX`): correctly reports zero completed samples before either sample's `hla_bam_read_count.csv` exists, and correctly picks up a sample the moment a simulated marker file is created. Full end-to-end dry-run confirmation was blocked by an unrelated, pre-existing `demo/` harness issue (`reference_files`' own dbsnp/gnomad provider resolution failing before DAG-build even reaches this module) -- confirmed unrelated by checking this module's own parse-time scope-summary line (`INFO [mhc_hammer]: ... in scope for this invocation`) still printed successfully both before and after this change, meaning the whole file (including the new rule) parses without error; the crash itself is entirely inside a different module's reference-file resolution.
- **Real design bug in `_mhc_hammer_patient_completed_samples` above, caught by a direct user question before it ever ran in production**: the first version derived `candidate_sample_ids` purely from the *current* invocation's own `CFG["paired_runs"]`, then fully overwrote the manifest with just that invocation's own newly-discovered completions. Asked directly: "What would happen if a subsequent run doesn't include one of the samples that was part of a previous run? Would it be excluded?" -- yes, it would have been: a sample recorded as completed in an earlier invocation, but absent from a later invocation's own sample subset (e.g. a different batch), would have silently vanished from the manifest on that later invocation's rewrite, even though its own `hla_bam_read_count.csv` was still sitting untouched on disk. This is the exact same class of bug `_mhc_hammer_cohort_table`'s own CHANGELOG entry already documents being fixed for a different file, and this rule made the identical mistake. Fixed by reading whatever's already in the existing manifest first and union-ing it with the current invocation's own newly-discovered completions, rather than replacing it outright -- makes the file a genuine, monotonically-accumulating record across differently-scoped batches. Verified directly with a real two-invocation simulation (not just reasoning about it): batch 1 with candidates A/B (both complete) produces `[A, B]`; batch 2 with a *different* candidate set (A/D only -- B entirely absent from this batch's own config) still correctly produces `[A, B, D]`, not `[A, D]`.
