## [1.0] - 2026-09-03

This release was authored by Ryan Morin.

- Ported HMF Tools' NEO ([hartwigmedical/hmftools](https://github.com/hartwigmedical/hmftools/tree/master/neo)) to native Snakemake rules -- neoepitope identification (point mutations + LINX fusion neoepitopes) and MHC class I presentation/binding scoring, from PURPLE somatic variants, LINX fusion neoepitopes, and LILAC HLA typing. Standalone module, not folded into `modules/lilac/1.0`, since NEO's real inputs are a cross-module-input problem (the same convention `lilac` itself already uses for `gene_copy_number`/`somatic_vcf`), not an internal detail of any single upstream tool -- see README for the full architectural reasoning.
- Installed via the bioconda package `hmftools-neo` (confirmed available up to `1.3`, matching the latest non-beta GitHub release). Real entry-point class names confirmed directly against the real jar and differ from the module's own README: `com.hartwig.hmftools.neo.epitope.NeoEpitopeFinder` (not `neo.cohort.NeoEpitopeAnnotator`) and `com.hartwig.hmftools.neo.score.NeoScorer` (not `neo.scorer.NeoScorer`). The installed `neo` wrapper dispatches to either from one binary based on whether the first argument is a fully-qualified class name.
- `inputs.linx_neo_epitope_file`/`somatic_vcf`/`lilac_tsv_file`/`purple_purity_file` are all **required** cross-module inputs (unlike `modules/lilac/1.0`'s own optional `gene_copy_number`/`somatic_vcf`) -- NEO cannot produce anything meaningful without real LINX/PURPLE/LILAC data, so there's no "run without it" fallback to support. Each pattern points at one real, specific file (not a bare directory) so Snakemake's own path-matching recognises it as a real dependency on whatever rule actually produces it, rather than requiring it to already exist as a plain, untracked source file.
- Added `_neo_pave_annotate`, this module's own copy of `modules/lilac/1.0`'s PAVE-annotation step -- NEO independently requires the same `IMPACT` VCF INFO tag LILAC needed (confirmed by reading `PointMutationData.isRelevantMutation()`/`NeoSampleTask.java` directly: `impact.WorstCodingEffect` is read straight from the PAVE-written `VariantImpact` tag). This module owns its own copy rather than cross-referencing `lilac`'s own PAVE output, consistent with how every module in this HMF Tools family keeps its own copy of shared logic, and correct regardless of whether `modules/lilac/1.0` is even included in a given runner.
- Confirmed NEO's own per-variant copy number comes from the somatic VCF's own PURPLE-written INFO tags (`variant.variantCopyNumber()`/`variant.adjustedCopyNumber()`, `PurpleVcfTags.SUBCLONAL_LIKELIHOOD_FLAG`, confirmed in `NeoSampleTask.java`; exact literal tag names traced through `VariantContextDecorator.java`: `PURPLE_CN`, `PURPLE_VCN`, `SUBCL`) -- **not** the separate `cnv.gene.tsv` gene-copy-number file whose schema drift broke `modules/lilac/1.0`'s own `gene_copy_number` input. `NeoScorer`'s own `-purple_dir` usage (`PurityContextFile`/`PurpleQCFile`/`PurplePurity`, confirmed in `hmf-common`) is a simple, schema-stable purity/QC file pair, not the gene-CN file either -- meaning this module is compatible with `modules/hmftools/1.1`'s existing PURPLE 2.54 output, unlike LILAC. **Confirmed against a real PURPLE 2.54 somatic VCF from a real GAMBL run** (`16-27229T--16-27229N--matched.purple.somatic.vcf.gz`): all three tags present in the header and populated with real values on real data rows (`PURPLE_CN=1.97;PURPLE_VCN=0.988;SUBCL=2.000e-03`) -- no longer just indirect evidence. The same real VCF confirmed only a SnpEff `ANN=` annotation is present, no PAVE `IMPACT` tag, confirming `_neo_pave_annotate` is doing real, necessary work rather than being redundant.
- Added two small, additive prerequisite rules to `modules/hmftools/1.1` (`_hmftools_linx_neo_epitopes`, `_hmftools_output_purple_somatic_vcf`) -- see that module's own `CHANGELOG.md` for the full detail, including why they're deliberately separate from `_hmftools_linx`/`_hmftools_purple_matched` themselves (to avoid forcing already-completed samples through those rules again under `--rerun-triggers mtime`).
- Real, verified-minimal `NeoEpitopeFinder` invocation (confirmed via the real jar's own registered-config-item dump): `-linx_dir`/`-somatic_vcf`/`-ref_genome_version`/`-ref_genome` are `REQUIRED`; `-ensembl_data_dir` is registered but not CLI-flagged required (kept anyway, matching the same functionally-required-but-not-CLI-flagged pattern already seen for PURPLE/PAVE).
- Real, verified-minimal `NeoScorer` invocation: its own registered CLI config has zero CLI-flagged-`REQUIRED` items at all -- confirmed via a real crash (`NullPointerException` in `BindScoreMatrix.loadFromCsv`) that `-score_file_dir`/`-score_file_id` is functionally required. `-lilac_dir`/`-purple_dir`/`-neo_dir` real directory requirements confirmed by reading `hmf-common`'s `LilacAllele.generateFilename()`/`PurityContextFile` directly (bare `<sample>.lilac.tsv` inside `-lilac_dir`, confirming `inputs.lilac_tsv_file` must point at `lilac`'s *internal* `02-lilac/` directory, not `99-outputs/lilac/`, which renames files to the full compound `{tumour_id}--{normal_id}--{pair_status}` prefix).
- RNA/isofox/`-cancer_tpm_medians_file` deliberately out of scope for v1 (README confirms graceful degradation to un-adjusted presentation likelihood without RNA) -- same DNA-only precedent already set for `modules/mhc_hammer/1.0` and `modules/lilac/1.0`.
- **Not yet independently verified** (flagged honestly, same standard as the `lilac` module's own iteration): the exact real filenames inside NEO's HMF resource bundle and the correct `options.score_file_id` (placeholder `cmb_02` used for now, matching the module's own README example); whether `-ensembl_data_dir` is truly required by `NeoEpitopeFinder` at runtime; whether `NeoScorer` produces valid output with RNA entirely omitted. (PURPLE 2.54's real somatic VCF INFO tags are now confirmed against real data -- see above.) All verified so far via real local dry-runs against demo data with simulated cross-module inputs (full DAG resolves, both NEO invocations render with correct real CLI syntax) -- real-run verification against actual cluster data is the next step, same escalation already used for `lilac`.
