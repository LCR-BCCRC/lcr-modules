# Changelog

All notable changes to the `neo` module will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.0] - 2026-09-03

This release was authored by Ryan Morin.

- Ported HMF Tools' NEO ([hartwigmedical/hmftools](https://github.com/hartwigmedical/hmftools/tree/master/neo)) to native Snakemake rules -- neoepitope identification (point mutations + LINX fusion neoepitopes) and MHC class I presentation/binding scoring, from PURPLE somatic variants, LINX fusion neoepitopes, and LILAC HLA typing. Standalone module, not folded into `modules/lilac/1.0`, since NEO's real inputs are a cross-module-input problem (the same convention `lilac` itself already uses for `gene_copy_number`/`somatic_vcf`), not an internal detail of any single upstream tool -- see README for the full architectural reasoning.
- Installed via the bioconda package `hmftools-neo` (confirmed available up to `1.3`, matching the latest non-beta GitHub release). Real entry-point class names confirmed directly against the real jar and differ from the module's own README: `com.hartwig.hmftools.neo.epitope.NeoEpitopeFinder` (not `neo.cohort.NeoEpitopeAnnotator`) and `com.hartwig.hmftools.neo.score.NeoScorer` (not `neo.scorer.NeoScorer`). The installed `neo` wrapper dispatches to either from one binary based on whether the first argument is a fully-qualified class name.
- `inputs.linx_neo_epitope_file`/`somatic_vcf`/`lilac_tsv_file`/`purple_purity_file` are all **required** cross-module inputs (unlike `modules/lilac/1.0`'s own optional `gene_copy_number`/`somatic_vcf`) -- NEO cannot produce anything meaningful without real LINX/PURPLE/LILAC data, so there's no "run without it" fallback to support. Each pattern points at one real, specific file (not a bare directory) so Snakemake's own path-matching recognises it as a real dependency on whatever rule actually produces it, rather than requiring it to already exist as a plain, untracked source file.
- Added `_neo_pave_annotate`, this module's own copy of `modules/lilac/1.0`'s PAVE-annotation step -- NEO independently requires the same `IMPACT` VCF INFO tag LILAC needed (confirmed by reading `PointMutationData.isRelevantMutation()`/`NeoSampleTask.java` directly: `impact.WorstCodingEffect` is read straight from the PAVE-written `VariantImpact` tag). This module owns its own copy rather than cross-referencing `lilac`'s own PAVE output, consistent with how every module in this HMF Tools family keeps its own copy of shared logic, and correct regardless of whether `modules/lilac/1.0` is even included in a given runner.
- Confirmed NEO's own per-variant copy number comes from the somatic VCF's own PURPLE-written INFO tags (`variant.variantCopyNumber()`/`variant.adjustedCopyNumber()`, `PurpleVcfTags.SUBCLONAL_LIKELIHOOD_FLAG`, confirmed in `NeoSampleTask.java`; exact literal tag names traced through `VariantContextDecorator.java`: `PURPLE_CN`, `PURPLE_VCN`, `SUBCL`) -- **not** the separate `cnv.gene.tsv` gene-copy-number file whose schema drift broke `modules/lilac/1.0`'s own `gene_copy_number` input. `NeoScorer`'s own `-purple_dir` usage (`PurityContextFile`/`PurpleQCFile`/`PurplePurity`, confirmed in `hmf-common`) is a simple, schema-stable purity/QC file pair, not the gene-CN file either -- meaning this module is compatible with `modules/hmftools/1.1`'s existing PURPLE 2.54 output, unlike LILAC. **Confirmed against a real PURPLE 2.54 somatic VCF from a real GAMBL run** (`16-27229T--16-27229N--matched.purple.somatic.vcf.gz`): all three tags present in the header and populated with real values on real data rows (`PURPLE_CN=1.97;PURPLE_VCN=0.988;SUBCL=2.000e-03`) -- no longer just indirect evidence. The same real VCF confirmed only a SnpEff `ANN=` annotation is present, no PAVE `IMPACT` tag, confirming `_neo_pave_annotate` is doing real, necessary work rather than being redundant.
- Added two small, additive prerequisite rules to `modules/hmftools/1.1` (`_hmftools_linx_neo_epitopes`, `_hmftools_output_purple_somatic_vcf`) -- see that module's own `CHANGELOG.md` for the full detail, including why they're deliberately separate from `_hmftools_linx`/`_hmftools_purple_matched` themselves (to avoid forcing already-completed samples through those rules again under `--rerun-triggers mtime`).
- Real, verified-minimal `NeoEpitopeFinder` invocation (confirmed via the real jar's own registered-config-item dump): `-linx_dir`/`-somatic_vcf`/`-ref_genome_version`/`-ref_genome` are `REQUIRED`; `-ensembl_data_dir` is registered but not CLI-flagged required (kept anyway, matching the same functionally-required-but-not-CLI-flagged pattern already seen for PURPLE/PAVE).
- Real, verified-minimal `NeoScorer` invocation: its own registered CLI config has zero CLI-flagged-`REQUIRED` items at all -- confirmed via a real crash (`NullPointerException` in `BindScoreMatrix.loadFromCsv`) that `-score_file_dir`/`-score_file_id` is functionally required. `-lilac_dir`/`-purple_dir`/`-neo_dir` real directory requirements confirmed by reading `hmf-common`'s `LilacAllele.generateFilename()`/`PurityContextFile` directly (bare `<sample>.lilac.tsv` inside `-lilac_dir`, confirming `inputs.lilac_tsv_file` must point at `lilac`'s *internal* `02-lilac/` directory, not `99-outputs/lilac/`, which renames files to the full compound `{tumour_id}--{normal_id}--{pair_status}` prefix).
- RNA/isofox/`-cancer_tpm_medians_file` deliberately out of scope for v1 (README confirms graceful degradation to un-adjusted presentation likelihood without RNA) -- same DNA-only precedent already set for `modules/mhc_hammer/1.0` and `modules/lilac/1.0`.
- **Fixed a real bug found while the user was setting up their own mirror**: `_neo_download_reference`'s output filenames (`train_<fileType>.<score_file_id>.csv`, with a placeholder `options.score_file_id: "cmb_02"`) didn't match NEO's real convention at all. Root-caused by reading `BindCommon.formFilename()` directly (`~/git/hmftools/neo/.../bind/BindCommon.java`): the real pattern is `neo_train_<fileType>.csv` (note the `neo_` prefix, and no id suffix) when `-score_file_id` is omitted -- `ScoreConfig.ScoreFileId` is an optional CLI item (`registerConfig` adds it with `required=false`), and `getScoringFilename()` only appends `_<id>` (underscore, not the originally-assumed `.`) when one is actually passed. Cross-checked against the real, current `hartwigmedical/hmftools` `pipeline/README_RESOURCES.md` NEO section, which lists the exact same 8 filenames with no id suffix -- confirming the *standard, publicly distributed* HMF resource bundle is generated and shipped id-less. Fixed by renaming `_neo_download_reference`'s 8 output files to the real `neo_train_*.csv` names and removing `-score_file_id`/`options.score_file_id` entirely (never passed to `NeoScorer`, matching the bundle). This is the file list to source when mirroring to `www.bcgsc.ca/downloads/morinlab/hmftools-references/neo/` -- get them from the [Oncoanalyser reference-data page](https://nf-co.re/oncoanalyser/docs/usage/#reference-data-urls) `README_RESOURCES.md` links to.
- **Fixed a real crash on the first real cluster run**: `_neo_pave_annotate` crashed with `htsjdk.tribble.TribbleException: "An index is required, but none found."` reading `inputs.somatic_vcf` -- root cause was in `modules/hmftools/1.1`, not here (see that module's own `CHANGELOG.md`: its `_hmftools_output_purple_somatic_vcf` symlinked the VCF without PURPLE's own companion `.tbi` index). Fixed on this side by adding `_neo_get_raw_somatic_vcf_index` and tracking it as a real (but CLI-flag-unused) `input:` on `_neo_pave_annotate`, so Snakemake enforces the index's existence/ordering via the same path-pattern-matching convention used for the VCF itself, now that `hmftools/1.1` actually produces it.
- **Found a real, currently-unresolvable upstream schema gap on the same real cluster run, immediately after the fix above**: once `_hmftools_linx_neo_epitopes`'s output was made readable (see that module's own `CHANGELOG.md`), `_neo_epitope_finder` crashed reading it -- `java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null`, in `NeoEpitopeFusion.fromLines()`. Root-caused by diffing the real writer (LINX 1.17's own `hmf-common` `NeoEpitopeFusion` class, checked out at the real `linx-v1.17` tag) against the real reader (NEO v1.3's own copy of the same class, checked out at the real `neo-v1.3` tag): LINX 1.17 writes 17 columns (`junctionCopyNumber` but no `copyNumber`); NEO v1.3 unconditionally looks up an 18th, `copyNumber`, via an unchecked `fieldsIndexMap.get("copyNumber")`. Checked every tagged LINX release through the current latest, **v2.3**, directly -- none of them write this field; only the current, unreleased `hmftools` `master` branch does (confirmed both the `hmf-common` class and LINX's own `NeoEpitopeWriter` construction call were updated together there). So this isn't a version we pinned wrong -- there is currently no real, installable LINX release that satisfies what NEO v1.3 expects for fusion-derived neoepitopes.
- **Decision (discussed with the user directly)**: skip fusion-derived neoepitopes rather than fabricate the missing `copyNumber` column or build LINX from `master` outside this repo's established pinned/bioconda-reproducible convention. `inputs.linx_neo_epitope_file` is now optional and existence-gated (`_neo_get_linx_epitope_file`, mirroring `modules/lilac/1.0`'s own `gene_copy_number`/`somatic_vcf` pattern) -- its default pattern is deliberately left pointing at a filename `_hmftools_linx_neo_epitopes` no longer produces (that rule's own `output:` was reverted to the real, underscore-named file LINX actually writes, and its compat symlink removed -- see `modules/hmftools/1.1`'s own `CHANGELOG.md`), so it will never resolve to a real file until a real LINX release closes the gap. `_neo_epitope_finder`'s `params.linx_dir` falls back to its own `output_dir` when no real LINX file is configured/found -- `-linx_dir` is still always passed (confirmed `NeoEpitopeFinder`'s CLI marks it `REQUIRED`), but `NeoSampleTask.getSvFusions()` (confirmed via its own real source) gracefully warns and returns an empty list when the sample's expected file isn't present in that directory, rather than crashing -- exactly the behaviour this fallback relies on. Point-mutation-derived neoepitopes (the `somatic_vcf` path, unaffected by any of this) remain fully functional.
- **Found and fixed a second real upstream schema gap, immediately after the fix above, on the same real cluster run**: once fusion-derived neoepitopes were skipped, `_neo_scorer` crashed reading `-purple_dir` -- `NullPointerException: Cannot invoke "com.hartwig.hmftools.common.purple.PurityContext.bestFit()" because "purityContext" is null`, preceded by `failed to read sample(...) purity data: NullPointerException ... Map.get(Object) is null`. Root-caused the same way as the LINX gap: diffed PURPLE 2.54's real writer (`PurityContextFile.java`, checked out at the real `purple-v2.54` tag -- the version `modules/hmftools/1.1` actually pins) against NEO v1.3's real reader (`PurplePurity.java`, checked out at the real `neo-v1.3` tag). PURPLE 2.54's own `purity.tsv` header has no `runMode`/`targeted` columns at all; NEO v1.3's reader does an unchecked `fieldsIndexMap.get()` for both. This is a much larger version gap than the LINX one -- PURPLE has since reached **v4.4** -- but unlike `copyNumber` (real, unknowable-without-rerunning-PURPLE biological data), `runMode`/`targeted` are deterministic run metadata this module already knows: `runMode` is always `TUMOR_GERMLINE` (`CFG["paired_runs"]` is narrowed to `pair_status == "matched"` only), and `targeted` is read straight off `{seq_type}` (capture vs genome). So this one is bridged rather than skipped: new rule `_neo_prep_purple_dir` writes a small `purple_compat/` directory per pair -- the real `purity.tsv` with these 2 columns appended, and the real, unmodified `.purple.qc` symlinked in alongside (confirmed `PurpleQCFile`'s own reader uses defaulted `getValue()` lookups, not the same strict `.get()` pattern, so it isn't affected by the same class of gap). `_neo_scorer`'s own `-purple_dir` now points at this compat directory instead of `hmftools/1.1`'s real PURPLE directory directly.
- **Not yet independently verified**: whether `-ensembl_data_dir` is truly required by `NeoEpitopeFinder` at runtime; whether `NeoScorer` produces valid output with RNA entirely omitted; whether `_neo_epitope_finder`'s own consumption of `_neo_pave_annotate`'s output VCF (not a relocated symlink, PAVE's own freshly-written file) hits the same index requirement -- PAVE is expected to write its own `.tbi` alongside its `.gz` output on the fly (standard htsjdk behaviour), but this hasn't been directly confirmed the way the PURPLE-VCF case now has. Whether any other `NeoScorer`/`NeoEpitopeFinder` code path touches further PURPLE/LILAC fields not yet exercised by a real run (the `runMode`/`targeted` gap was only found because `-purple_dir` is actually read; other, still-unexercised paths could reveal further version gaps the same way). (PURPLE 2.54's real somatic VCF INFO tags, and the real reference-bundle filenames, are both confirmed against real data/source -- see above.) Real-run verification is proceeding incrementally, one real crash and fix at a time, same escalation already used for `lilac`.
